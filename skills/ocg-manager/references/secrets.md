# Keep credentials out of the conversation

Treat upstream API Keys, Gateway Access Keys, admin passwords, migration passphrases, `.encryption-key`, session cookies, and OAuth data as secrets. The agent may know **where** they are stored and whether a safe status says they are present, but should not learn their values.

1. Never ask the user to paste a secret into chat. Do not put a secret in a tool argument, shell command, script literal, URL, issue, artifact, or test output. Masking a value *after* a tool returns is too late: the original tool output has already entered the conversation.
2. Prepare names, URLs, ports, models, proxy choices, and target client settings first. Let the user type the secret into the local dashboard or the client's password/Key field. While they do so, do not inspect that field, capture a page/screenshot showing a revealed Key, read browser network traffic, or copy the page's response JSON. Resume with a nonsecret completion signal or masked state.
3. Do not run `key add <name> <key>`, `--password <value>`, `--encryption-key <value>`, `status --show-key`, or an authenticated `curl` with the Key from agent tools. For a release without default Key hiding, do not capture `serve`/`status` output; the user runs it in a private terminal. `status --help` reveals whether `--show-key` exists without revealing a Key.
4. Avoid raw Docker logs, `docker compose config` output, `.env`, database/backup dumps, and unredacted diagnostics. In newer CLI builds `serve` and ordinary `status` hide the Gateway Key; old logs can still contain it. If a safe tool supports output filtering **before** content enters the agent context, inspect only the needed status. Otherwise have the user inspect locally and report a nonsecret result.
5. Do not claim that local storage is a remote vault. The data directory and `.encryption-key` together can restore encrypted account credentials; browser profiles hold unencrypted session cookies. A Gateway Key shown in Access Center is a client credential, not the upstream Key.

If a real Key was already pasted into a chat, tool output, or shared log, do not quote it again. Identify which credential it is, advise rotation at its issuing authority (and replacement in OCG or connected clients), then verify the new credential through a private handoff. Do not promise that deleting a message or redacting a later answer removes earlier exposure.

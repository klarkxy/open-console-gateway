# Runtime Invariants

Behavioral invariants of the running system. Read this before changing gateway routing, aliases, Zen Free, the plan catalog, access keys, outbound proxy, or usage sync. Code is the source of truth; this page maps semantics that are easy to get wrong.

## Gateway And Model Lists

- Core Gateway: Axum + Tokio + reqwest. The same port exposes OpenAI Chat Completions / Responses, Anthropic Messages, Gemini `generateContent` client entrypoints, and Claude Desktop alias entrypoints.
- Authenticated `GET /v1/models` lists currently-routeable Aliases authorized by the original static OpenCode Go protocol table plus the sealed MiniMax CN, Kimi CN, and selected GOAT long-name maps, then merges public models from saved user-defined Providers and model IDs declared by eligible Custom accounts (enabled+ready+non-empty Key; verification is optional). Saved Zen `-free` rows keep the exact raw pin and publish the suffix-stripped Alias; saved Command rows may join any code-owned Alias; saved MiniMax/Kimi rows activate only exact code-owned CN mappings. Unmatched Command/MiniMax/Kimi rows remain exact raw pins and are not advertised as new Aliases. Protected `GET /dashboard/api/v3/application-models` is **Go-routable Aliases ∩ current pricing snapshot** (highspeed inherits base-price rows; empty intersection is `[]`), excluding Custom, user-defined Providers, and the CN Plans. Neither GET path makes upstream requests; catalog refreshes are explicit control-plane actions. Custom IDs come from eligible accounts' declared capabilities. Unknown model names return `400` on all supported client formats.
- Custom model identity: an eligible Custom capability has a public model name and an exact `upstream_model`. `/v1/models` publishes only the routeable public name. Discovery yields upstream IDs and imports `public_model = upstream_model` exactly; it performs no suffix stripping or Alias synthesis. Raw conflicts are excluded from publication and resolve fail-closed as `ambiguous_model_id`. The Providers Alias tab is a read-only aggregation of existing contracts and capabilities.
- Gemini clients use `/v1beta/models/{model}:generateContent` or `:streamGenerateContent` (`/v1/models/...` also accepted), may auth with `x-goog-api-key`; Gemini is only a client format, and Gateway always converts to the known model's recommended upstream protocol. Unknown model names return `400` on Chat / Responses / Messages / Gemini.
- Model protocol capabilities are hard-coded in `ocg_domain::protocol::MODEL_PROTOCOLS` (`ocg-core` `kernel/protocol.rs` and `gateway/protocol.rs` are facade/host conversions): `preferred` matches the official Go docs endpoint table; `supported` is the checked-in set verified with a test account, including 2026-08-27 Go `live_supported` extra Chat/Messages/Responses paths, while later explicit probe observations are persisted separately. If the client protocol is enabled, the request passes through; otherwise the gateway converts to the model's preferred protocol, then to the first remaining enabled protocol in adapter fallback order. CPA is unchanged: it preserves supported Chat, Responses, and Messages client protocols and converts Gemini to Chat. The request path uses the saved contract; a protocol probe would double-bill. `grok-4.6`, `grok-4.5`, and `gpt-5.6-luna` are Responses-only, so a Chat entry converts. `MODEL_PROTOCOLS` still only serves OpenCode Go; Go/Zen refresh-discovered IDs that are unknown to the table are materialized with the provider-level default protocol (Chat Completions) as available, and the refresh-written default-off overrides keep them disabled until explicitly enabled. The whole-document JSON conversion kernel is in `ocg-gateway`.
- Every OpenCode Go inference attempt carries `x-opencode-session`. An existing client value wins; otherwise the Gateway maps OpenCode's custom-Provider `x-session-id` / `x-session-affinity`, derives a stable private digest from the conversation seed, or uses the request ID only when the request has no usable conversation seed. Zen Free uses the same session header plus the official anonymous-channel identity headers (`User-Agent` containing `opencode`, `x-opencode-client`, `x-opencode-request`, `x-opencode-project`). Client-supplied OpenCode values win; otherwise the Gateway fills them after account selection (synthesized `User-Agent` is `opencode`, `x-opencode-client` is `cli`, request/project fall back to the request ID / session). Other Providers do not receive these headers. This Provider-specific identity is added only after account selection.

One logical client request captures `RequestSnapshots` at entry (`crates/ocg-core/src/gateway/executor.rs`). Fallback iterations re-read live account state; they do not recapture the frozen row.

| Frozen at entry | Re-read each fallback iteration |
| --- | --- |
| `AppConfig` | accounts |
| pricing snapshot | eligible Custom runtimes |
| `ForwardRouteSet` | Zen Free cooldown |
| provider contracts | current account availability |
| resolved Alias / raw identity | — |

## Dashboard V3 And V2 Tombstones

- Connection and model/protocol probes require a successful JSON response matching the requested protocol: Chat choices with message objects, Responses output without a failed/cancelled/pending status, or a Messages assistant message with content blocks. Arbitrary JSON and non-null error objects do not certify a connection. Custom/dynamic draft probes are capped at 30 seconds per request (or the shorter configured timeout) and do not persist routing or discovered models. Responses probes use a 16-output-token budget to satisfy the observed compatible-upstream minimum. Go/Zen probes share production provider identity headers; other providers receive no OpenCode identity headers. Rotating a Custom or user-defined Key, or changing that connection's Endpoint/protocol, deletes that account's `custom_endpoint` probe observations and bumps the contract-scope revision so the old success cannot authorize the new Key or URL. Built-in catalog evidence is not wiped when a Go Key rotates.

- Dashboard V3 is mounted at `/dashboard/api/v3`. Control-plane changes require CAS (`expectedRevision`, `processGeneration`; price writes also need `expectedPricingRevision`). `ConnectionInfo` is the only V3 response DTO allowed to return the plaintext Open Console Gateway Key; Key-mutation responses do not include plaintext, and the client re-fetches `GET /connection`. Creating or rotating a managed CPA client Inference Key returns that CPA secret once. `GET /contract` returns the current process's live revision / generation token.
- Dashboard V4 is mounted at `/dashboard/api/v4` as a parallel additive control plane. It reuses V3 session middleware and its listings return the same `ControlRevision` tokens V3 uses for CAS. V4 mutations use those same CAS tokens. `POST /onboarding/commit` is idempotent by `operationId` with payload-digest binding evaluated before CAS; the same id with a different payload is rejected (`409` `operationPayloadMismatch`) and never replays. All objects of one commit land in one SQLite transaction; responses and stored results are secret-free. Built-in and Custom API connections are not writable through V4 in this stage. V3 `$defs` and routes stay frozen. Read-only routes remain `GET /contract`, `GET /templates`, `GET /connections`, and `GET /accounts`; those reads perform no outbound requests. Connection ids are deterministic UUIDv5 values derived from the legacy identity, never from names or URLs. Built-ins without accounts are templates, not connections; Custom accounts are never merged by URL. Eligibility and authorization are local projections: `unknown` is not `valid`, and eligibility is never upstream health. `GET /accounts` is the identity list (`IdentityList`); `authState` is local (`unknown` is never `valid`; `valid` requires the existing verification record). `POST /credentials/{id}/rotate` is CAS-only (no `operationId`): same credential/binding ids, incremented `version` and `authStateVersion`, `authState=unknown`, and cleared account auth/verification so the old version cannot pollute the new Key. `PATCH /bindings/{id}` is the same CAS style and edits `modelScope` / binding `enabled` independently. `POST /identities/{id}/credentials` adds another Key that reuses the identity and joins its quota pool. The dashboard consumes this control plane for the Providers rail, user-defined Provider creation, and the Accounts-page identity overlay (`GET /accounts`); Accounts mutations stay on V3. Gateway shadow planning (`gateway::shadow`) can compare a live `AttemptSpec` to a rematerialized plan without sending a second request; it is thread-local default-off and never dual-sends.
- Provider catalog in V3 is the single `ProviderCatalog` row, populated by reading the unified `providers` table (schema v42) and joining it with sealed `BUILTIN_PROVIDERS` facts. Each `ProviderCatalogEntry` carries `origin` (`builtin` | `preset` | `custom`), `editable`, `deletable`, and the row's `offering` (`plan` | `api`). Builtin rows are always `editable=false` / `deletable=false`; dynamic rows are always editable and deletable. `GET /providers/{id}` returns the union view: a builtin row yields its sealed definition; a dynamic row yields the persisted `ProviderDefinition`. `PATCH /providers/{id}` and `DELETE /providers/{id}` reject any builtin id with `400` + `code="builtinProviderImmutable"`. Builtin adapters never flow through this route. The Providers rail renders the V4 connection projection: built-in Providers with at least one account, every user-defined Provider (with or without a Key), and each Custom API account as its own row, grouped by Plan/API. Unused built-in templates remain only in the Add catalog. `POST /providers` saves the definition; a Key on keyed auth still creates the first account in the same write, while omitting `key` leaves the definition without an account. The dashboard's create flow uses the V4 onboarding commit; V3 `POST /providers` remains supported for API clients. No-auth still creates the singleton account. Deleting the last account does not delete the definition. The only "add provider" entry opens the preset browser in the main area (embedded preset form or manual form) and collects an optional Key on keyed auth. Detail is unified for every origin: models, pricing (only when `pricingAvailability=available`), and settings (which absorbs the OpenCode invite link; the legacy **Other** tab is gone). Deep links carry `connection` / `tab` / `add` / `preset`; a legacy `provider` value resolves on read to the built-in or user-defined connection with that legacy id; legacy `scope_kind` / `scope_id` values are mapped on read.
- Node migration is V3-only at `POST /accounts/transfer/export|preview|import` and loopback-dashboard-only; forwarded scheme headers never grant access. Export has no administrator step-up. The dashboard receives a version-1 Argon2id (64 MiB, 3 iterations, one lane) plus AES-256-GCM envelope with fixed AAD, never plaintext account or Access Keys. Password work is process-wide single-flight and runs outside settings/SQLite locks; every response is `Cache-Control: no-store`. Preview and import share decrypt/validation. Import rechecks CAS after KDF and writes the database-owned merge in one SQLite transaction. Payload V2 established stable-ID identity: package fields win on matching account/Access-Key IDs; same Plan/name with different IDs coexist; existing destination account IDs keep their current order and source-only IDs append in package order. Destination-only Access Keys and Provider scopes remain. Different-ID Key value collisions, more than 64 active sub Keys, in-bundle duplicate IDs, or any invalid row reject and roll back the whole database merge. V2 carries usable ordinary accounts and verification state, ready account Keys, primary/active sub Access Keys, portable config, Zen Free state/catalog, and Provider catalogs/evidence/overrides. Matching destination rows retain local browser data plus usage/cooldown history; stale authentication and last-error flags clear with package-owned account credentials. Source browser profiles/cookies, login passwords, referral codes, logs, usage, cooldown state, and unfinished managed drafts are omitted. Destination listener/root URL and OS-owned auto-start/Dock settings remain local. All fallible runtime snapshot construction reads the uncommitted merged transaction; only after it succeeds does SQLite commit, followed by an infallible snapshot installation and one revision bump.
- Current export refinement: the cryptographic envelope remains version 1, while newly exported portable content is payload V5 (V4 import remains supported) with `providerId` only. The payload also carries an optional/defaulted user-defined Provider definition collection (id, name, Endpoint, protocol, auth kind, mappings) plus those Providers' portable accounts. Export includes every saved definition. Import validates each definition through the typed dynamic Provider validator, binds only Configurable HTTP, rejects dangling/unknown IDs, and merges inside the same SQLite transaction: package fields win for matching definition IDs; different IDs coexist even with the same display name; destination-only definitions and accounts remain. If a matching definition crosses the keyed/no-auth boundary, every destination account that references it must also be present in the package; otherwise import fails closed rather than inventing or fanning out an account Key. Decrypt/validation rejects payload V1–V3 and any other version except 4 or 5 (including a future V6 package from a newer exporter) with a distinct unsupported-version `400` that names the found version and the current expected version; that error is not a wrong-password or damaged-file result. This binary still exports payload V5 and does not emit V6.
- Platform parents and links remain account-owned Custom HTTP configuration. Payload V5 carries their portable definitions and links, excluding management credentials and snapshots; imported group evidence is unverified. A package that reuses a destination platform parent ID with a different site or kind is an explicit preview/import conflict; the SQLite merge writes nothing. Each linked attempt freezes its exact model/group price, retains only native-currency estimates, and never infers wallet debit or USD cost. Refresh is manual and guards parent/link/Key identity before persisting observations.
- Legacy protected V2 REST (`/dashboard/api/...`, excluding V3 and V4) returns structured `410` (`code=dashboardV2Removed`) to authorized dashboard sessions; anonymous requests get `401` first. V2/V3 auth and session, browser WebSocket, and inference entrypoints keep their existing semantics. The only preserved unversioned paths are exact `auth/status|register|login|logout` and `browser/sessions/{token}/ws`.
- `crates/ocg-core/src/dashboard.rs` handles SPA `index`/`assets` and preserved V2 auth and browser WS handlers; the tombstoned V2 REST middleware lives in `host_router.rs`. Provider model/protocol probing is the low-frequency V3 path `POST /providers/{provider_id}/protocol-probes`: it rejects models outside the effective Provider catalog, exposes no account selection, may walk routing-eligible accounts in saved order, and persists observations without changing protocol enablement or preference. The Accounts page uses the separate operational path `POST /accounts/{id}/model-tests` with only `{ modelId }`. It admits the model against that exact account's current scope, derives the effective protocol, and sends one minimal request through only that account. It mutates no control-plane state, so it has no CAS; it never selects a sibling account, performs Gateway fallback, changes cooldown/verification/enablement, or writes Provider evidence. The dashboard sequences **Test all** client-side and keeps results only in the open dialog. Retired V2 account paths still return `410` after authorization.
- Request observability belongs exclusively to `forward_logs`: forwarded attempts, provider protocol probes, and authenticated local parse/validation/routing failures must not be duplicated into `gateway_logs`. Pre-selection failures use unresolved/Gateway attribution with zero token fields and `cost_state=not_applicable`. `gateway_logs` is reserved for operational lifecycle/control-plane events and failures to persist or finalize a request-log row. Unauthorized requests and expected local fallbacks remain unpersisted.

## Access Keys And Auth

- On loopback listeners, every Dashboard API request (including public registration/login) requires a single `Host` naming `localhost` or a literal loopback IP. If `Origin` is present it must use HTTP/HTTPS and match that Host and port; cross-site Fetch Metadata is rejected. Native local requests may omit Origin. Forwarding headers disable local login bypass and require the existing Dashboard session. Vite preserves its original Host and Origin when proxying local development requests. Public-host reverse proxies must target a non-loopback listener, whose single-admin login remains unchanged.

- From schema v27 the authoritative table is SQLite `access_keys` (primary Key fixed id `gateway_keys::PRIMARY_KEY_ID` / `00000000-0000-0000-0000-000000000001`, name snapshot "Primary", never disable/delete; sub-Keys are non-primary rows, active limit 64, soft-delete keeps the name but clears plaintext). Sanitized config JSON stores `gateway_key` as `""`. In-process `AppConfig.gateway_key` and `GET /dashboard/api/v3/connection` expose the live primary Key. Lifecycle is only through `/dashboard/api/v3/keys*` (including `POST /keys/primary/regenerate`). Primary/sub Key value mutual exclusion is enforced by `gateway_keys::ensure_primary_value_allowed`. v27 copies historical `sub_gateway_keys` rows into `access_keys` and drops that table.
- Auth collects all non-empty candidate headers Bearer / x-api-key / x-goog-api-key; any match against the credential snapshot (`CoreStateInner.credential_snapshot`, including primary Key and enabled sub-Keys) passes, with attribution to the first match in candidate-header order; the same snapshot feeds the forward log name snapshot.
- Non-loopback listeners use single-admin login. Docker can be first-initialized via `OCG_ADMIN_USERNAME` and `OCG_ADMIN_PASSWORD` (both must be set together; setting only one causes a startup error); when not provided the first registered user becomes admin.

## Persistence

- Schema v41 persists a selected preferred protocol separately from enablement. Dashboard model-override items may set preferred=true on exactly one supported protocol per model. Preference and overrides commit together; omitted/false preserves it, static reset clears it, and V5 node transfer carries it. The effective preferred protocol uses this choice, including while disabled. Go/Zen default-Chat materialization applies only when no static profile exists; Zen additionally requires a -free model. Explicit NO_PROTOCOLS profiles remain unavailable. Dynamic account DTOs omit synthetic purchase/expiry dates while preserving their stored compatibility anchors. The v42 rebuild preserves this table but drops the v41 `provider_id` CHECK (rows may now belong to builtin or dynamic ids). v43 widens `protocol` to `chat_completions | responses | messages` and restores Auto on MiniMax/Kimi exclusive-radio `force_off` siblings.

- Identity model (schema v45): a legacy account still backfills as one identity + one credential + one All-scope binding. New ids are deterministic UUIDv5 values in the same namespace as connection ids. The `accounts` row remains the physical Key-material holder; satellite rows are written in the same transaction as the account insert via the single `ocg-domain::credential` mapper (shared with migration). A confirmed identity may hold more than one Key: `POST /dashboard/api/v4/identities/{id}/credentials` creates another `accounts` row that reuses `identity_id` (a second product when `connectionId` differs). Platform parents and linked Keys stay separate identities: the parent holds a `platform_observer` credential (never used for inference); a linked Key's identity is `declared` with `authority_site` = parent `base_url`; the relation is declared, not verified. Do not auto-merge identities by URL, name, or key prefix, and do not claim a verified wallet. Cooldown columns stay on `accounts` and are projected as quota windows (not moved). Backfill creates one quota pool per identity (`relation_confidence` unknown, `policy_mode` authoritative_limit); a second credential joins that same pool and raises confidence to declared. A cooldown/429 written for one member fans out to the other members. Shared quota is evidence from pool membership, never from matching names. Routing skips an account when its inference binding is disabled or its `model_scope` does not allow the public/routing model; default All + enabled preserves previous routes.
- Current schema is **v45** (v45 additively creates identity/credential/binding satellite tables; v44 added the `dashboard_operations` idempotency ledger; see `storage-migration.md`). v33 added non-null `account_model_capabilities.upstream_model` and backfilled it from `model_id`. v34 adds the singleton `cpa_integration` row; CPA inference credentials, enablement, and order remain on its reserved account, while its model snapshot stays in `provider_model_catalogs`. v35 collapses Provider/Plan identity to `provider_id` only after a fail-closed preflight of known v34 pairs and a unique pre-v35 snapshot on non-empty libraries. v36 additively created `ollama_cloud_usage_state` for the unreleased Cookie-usage scrape; v37 drops that table and adds `ollama_cloud_billing` (account-scoped Free/Pro/Max/Team). Creating an Ollama account writes the account row, any Custom contract data, and `ollama_cloud_billing` in one SQLite transaction; a billing write failure rolls back the new account and leaves `settings_revision` unchanged. Same-tier updates stay a separate account write. v42 unifies the typed user-defined Provider table with a sealed-Adapter seed catalog: it renames `dynamic_providers` / `dynamic_provider_models` to `providers` / `provider_models`, adds `origin` (`builtin` | `preset` | `custom`), `adapter_kind`, `offering` (`plan` | `api`), and `endpoint_per_account` columns, seeds the seven sealed builtin adapters (excluding CPA, the static external integration) as `builtin` rows whose attribute columns are display mirrors of the sealed registry, and filters dynamic read paths by `origin IN ('preset', 'custom')` so routing, V5 export, and existing API behavior are unchanged. The v41 `provider_model_protocol_preferences` provider_id CHECK is dropped (now that `origin` is queryable, a row may belong to a builtin or dynamic id); the protocol CHECK on `(chat_completions | messages)` is kept. Non-empty v41 databases get a unique `data.sqlite.pre-v42.<UTC>.bak` plus `.sha256` sidecar before the rewrite; fresh empty databases skip the snapshot. v40 added nullable `dynamic_provider_models.upstream_override`; v39 added `preset_id`; v38 added `platform_accounts` / `platform_links`; v41 added the per-scope `provider_model_protocol_preferences`. Neither migration synthesizes Aliases. See `storage-migration.md`.
- SQLite migration history through **v35** remains in place: v27 copied the primary Key and `sub_gateway_keys` into `access_keys` and dropped the legacy five `usage_sync_*` columns on `accounts` (official usage-sync metadata is now in `provider_usage_sync_state`). v29 removed SCNet Token Plans and deleted existing SCNet account rows. v30 introduced the temporary Custom multi-protocol JSON set. v31 added `provider_contract_model_protocol_overrides` and stopped reading the `provider_contract_scopes` switch columns. v32 replaced each Custom row with `endpoint_url` plus one `upstream_protocol`; historical rows choose Chat, then Responses, then Messages, append the corresponding standard inference path, clear non-selected Custom protocol evidence/overrides/capabilities, and become disabled/pending. v35 removes the offering dimension after a fail-closed pair preflight. Existing non-empty DBs generate a non-overwriting `data.sqlite.pre-v3.<UTC>.bak` plus `.sha256` sidecar before v27, and a unique `data.sqlite.pre-v35.<UTC>.bak` plus `.sha256` sidecar before the v35 rebuild; fresh empty DBs are created directly at the current schema without those copies. GUI data directory is Windows `%USERPROFILE%\.ocg-mgr` or macOS/Linux `~/.ocg-mgr`; CLI defaults to `~/.ocg-mgr-cli`. Upgrade, backup hashing, and failed-rollback are covered in `docs/maintainer/storage-migration.md`.
- Local account `key_cipher` / `password_cipher` uses AES-256-GCM with prefix `v2:` and body `base64(nonce || ciphertext || tag)`. The 32-byte AEAD key is SHA-256(domain || Host seed) from MachineBound / StaticKey material; the legacy FNV mixer is not used for v2. Encrypt always writes v2. Decrypt accepts `v2:` only via AEAD (authentication failure is an explicit error, never a UTF-8 guess) and still reads unprefixed legacy XOR of the old 16-byte-nonce shape so directory backups restore. A successful `open_with_cipher` rewrites remaining legacy account rows to v2 in one SQLite transaction and does not log plaintext Keys. Wrong-host or corrupt ciphertext fail closed. Portable node transfer stays envelope v1 / payload V5 and is unchanged.
- Downstream access root URL priority: non-empty `OCG_CLIENT_ROOT_URL` > SQLite manual value > frontend auto-derived from production origin / dev Gateway port. Environment-variable overrides are read-only and must not be written back to SQLite.
- Desktop Gateway port priority: valid `OCG_GATEWAY_PORT` > SQLite `gateway_port` (default `9042`). The desktop Host and Vite development proxy read the same variable. The override is read-only, must not be written back to SQLite, and does not change CLI `serve --port` semantics.

## Desktop Host

- Tauri v2 cross-platform tray app; the main window is hidden by default; tray/single-instance logic opens `http://127.0.0.1:<port>/dashboard/` in the system browser, and loopback listeners skip login automatically. Host capabilities (gateway lifecycle, native browser, autostart, Dock, updater) are registered into `CoreState` and **not** registered as `#[tauri::command]` / `invoke_handler`.
- The Settings page checks the latest GitHub Release via protected `GET /dashboard/api/v3/settings/check-update`. Installed desktop builds with the updater public key built in can download, verify the signature, and install in place; dev builds, CLI, Docker, and old versions not yet in the update channel keep the release-page / manual-overwrite path.

## Outbound Proxy

- Global outbound proxy is stored in `AppConfig`, with modes auto (system/environment), manual HTTP, force-direct, and per-model list (List). Non-List modes are mutually exclusive three-way; in List mode (`proxy_list_direction` allow/deny list + `proxy_list_models` known model ids), listed models take the direction exception segment (allowlist → proxy / denylist → direct), while unlisted models and non-model outbound (account test/verify, Zen Free manual model refresh, usage, pricing, updater download) take the direction default segment (allowlist → direct / denylist → proxy). List membership validation only runs at the dashboard `PUT /dashboard/api/v3/settings` write gate (non-empty, exact known ids, deduplicated); load paths tolerate stale values. Zen Free only hits the fixed `https://opencode.ai/zen/v1/models` when an admin explicitly refreshes, without a Key, not following redirects, and preserves the old snapshot if the refresh fails or returns empty. reqwest paths go through `ocg-core`'s `http_client.rs` facade into `ocg_infra::http`'s route set / `configured_builder`; the Tauri updater uses its `proxy` / `no_proxy` to align with the default segment and must not bypass per-account config. Forwarding picks routes from the request-entry snapshot; hot config switches do not affect in-flight requests. Custom HTTP (`custom.rs` + `custom_http.rs`, transport may reuse `ocg_infra::inference_http`) follows the same proxy policy; never follows redirects; never forwards dashboard/client auth; derives one auth header from the selected protocol (Bearer for Chat/Responses, `x-api-key` for Messages); and clamps timeout by `connect_timeout_secs` to 5–60 seconds. Any secret-bearing inference attempt — including OpenCode Go and other builtin keyed adapters — uses no-follow: a cross-origin `Location` must not receive `Authorization`, `x-api-key`, or query secrets. Zen Free remains keyless and may still follow when its adapter allows it. A model or endpoint override that leaves the connection/binding allowed-origin set (or the persisted validated Custom / dynamic URL) refuses to send the Key; sealed adapter origins stay sealed (official origin or the documented loopback test seam). Custom and dynamic user URLs reject metadata, link-local, unspecified, and opaque IPv4-trick hosts (`169.254.169.254`, `metadata.google.internal`, `0x…` / dword forms) before outbound. Documented loopback / LAN local-model destinations stay allowed and do not widen those exceptions to arbitrary custom hosts.

## Plan Catalog And Custom API Boundary

- Plan catalog is in static `ocg_domain::provider::BUILTIN_PROVIDERS`: OpenCode Go, Zen Free, Command Code GOAT, MiniMax CN Token Plan, Kimi Code CN, Custom API, and the static CPA external integration, plus runtime-persisted user-defined Providers. Internal identity is `provider_id` only (opencode, opencode-zen-free, command-code, minimax, kimi, custom, cpa, or a saved dynamic UUID). **The Adapter Registry stays static and sealed.** The unified `providers` table (schema v42) holds every row — builtin seed rows, preset-derived dynamic rows, and custom dynamic rows — in one place; each row carries `origin` ∈ {`builtin`, `preset`, `custom`}, `adapter_kind`, `offering` ∈ {`plan`, `api`}, and `endpoint_per_account`. Builtin seed rows are display mirrors of the sealed `BUILTIN_PROVIDERS` registry (the `endpoint_url` / `upstream_protocol` / `auth_kind` columns exist for symmetry and are populated from sealed constants); traffic and routing still resolve exclusively through the sealed adapter code constants, never through the seeded row. Dynamic rows (origin `preset` or `custom`) bind `ConfigurableHttp` and behave exactly as the pre-v42 typed user-defined Providers did. The static CPA external integration is not seeded: it is its own static product surface, never a row, and never appears in the Provider catalog. Typed Provider definitions may be persisted at runtime (`providers` / `provider_models` on schema v42) and dynamic rows always bind Configurable HTTP. Unknown provider IDs fail closed unless they match a saved dynamic definition or a sealed builtin id. User scripts, plugins, and binaries are never loaded. User-defined Providers are unpriced/unknown: no official usage, quota estimate, or pricing rows. Discovery and real model tests are optional control-plane actions and never gate save; a real test may consume upstream quota. Provider-owned Endpoint/protocol/auth/mappings are edited on Providers; account Key/enablement/order/notes stay on Accounts. A Provider update Key is accepted only for the required none-auth → keyed transition and is written to that singleton account; an already-keyed Provider rejects any non-empty update Key and never overwrites one or all accounts. Key rotation remains on Accounts. No-auth definitions expose one singleton account. Dynamic Provider create/update/delete construct the post-mutation runtime snapshot before SQLite commit, commit once, install that snapshot infallibly, reset routing, and bump `settings_revision` once; a failed precommit construction leaves DB, memory, and revision unchanged. Command Code GOAT is routable and its public official `GET /models` is Provider catalog discovery, not stored-Key verification; historical GOAT verification states normalize to `not_required`, and inference 401/403 remains the actual Key-auth boundary. Accounts contribute enabled+ready+non-empty-Key credentials and ordering, while the Provider model/protocol contract owns model supply. The GOAT included-model preset defaults on; additional discovered rows default off and require an explicit `force_on`. There is no account-level GOAT/All or Max entitlement mode. A verified GOAT pricing snapshot supplies per-request price-and-multiplier accounting and never falls back to Go pricing. Command Code exposes no machine-readable account-usage endpoint, so GOAT usage availability is `local_state`, never authoritative: the dashboard projects priced OCG request logs into the public `$14 / $35 / $70` windows and permits manual baseline correction. Unpriced rows and traffic outside OCG are omitted; the estimate does not affect inference eligibility or start automatic sync. All persistence mutation paths still reject enabling a truly `routable=false` static Provider before write, revision, or timestamp changes; the desktop UI only mutates via Dashboard V3 HTTP.
- MiniMax (`minimax`) and Kimi (`kimi`) are separate sealed adapters, not Custom presets. Both use Bearer Keys, fixed no-redirect official origins, Chat Completions plus Anthropic Messages (no Responses path), authenticated explicit `/models` refresh, generic provider cooldown on 429, and unpriced forwarding. MiniMax Chat uses `https://api.minimaxi.com/v1/chat/completions` and Messages uses `https://api.minimaxi.com/anthropic/v1/messages`; Kimi uses `https://api.kimi.com/coding/v1/chat/completions` and `/v1/messages`. The MiniMax sealed map covers `MiniMax-M3`, M2.7/M2.5/M2.1 standard and highspeed variants, and `MiniMax-M2` with matching lowercase kebab Aliases. Kimi maps `kimi-for-coding` → `kimi-k2.7-code`, `kimi-for-coding-highspeed` → `kimi-k2.7-code-highspeed`, `k3` → `kimi-k3`, and `k3-256k` → `kimi-k3-256k`. Forwarding always preserves the exact upstream ID. MiniMax manually reads `https://api.minimaxi.com/v1/token_plan/remains`; Kimi manually reads `https://api.kimi.com/coding/v1/usages`. Bounded responses replace only the same account/provider source snapshot under V3 CAS. These windows are display-only: there is no automatic sync and they never affect inference eligibility. Other Kimi/GLM ordinary or private endpoints remain Custom API concerns; GLM has no built-in Plan.
- Custom API (`custom`, `routable=true`) is a trusted-admin destination with one HTTP/HTTPS API URL and one `chat_completions` / `responses` / `messages` protocol per account; valid new accounts default enabled. Embedded credentials, query, fragment, redirects, metadata/link-local targets, and opaque IPv4-trick hosts are rejected; dashboard/client auth is never forwarded. A persisted Custom URL is the origin grant for that account's Key. Chat/Responses construct only Bearer auth, Messages only `x-api-key`; there is no auth override or retry. A root URL resolves through `/v1` plus the selected protocol path; a base already ending in `/v1` does not duplicate the segment. Existing complete standard or non-standard Endpoints remain verbatim, with non-standard paths retaining manual model entry. The single protocol is uniform across every declared model and is the effective preferred protocol: matching client wire passes through; other supported client formats, including Gemini, convert to it. Custom config and the complete model-capability list replace atomically under one V3 CAS write. Model discovery uses `/v1/models` for root/versioned bases or the sibling `/models` for a standard complete Endpoint; it does not guess from non-standard complete paths. Custom per-model overrides may only target the account's declared protocol; `force_on` cannot expand beyond that declaration, while `force_off` makes the model unroutable with no fixed-order fallback. Eligible accounts (enabled+ready+non-empty Key) dynamically route their declared model IDs. Custom cost/usage is unpriced/unknown and does not deduct provider quotas. A Custom account has one API URL and one protocol. Multi-endpoint providers belong on a static Provider Adapter.
- Custom API stays account-owned: Accounts is the sole Custom mapping editor and atomically stores one account-wide protocol with public-name → exact-upstream-ID rows. Providers and Aliases display only the read-only Custom aggregate with no edit action. Accounts still honors a `?view=accounts&account_id=<id>` deep link: it opens the matching account editor, closing clears `account_id`, and a stale ID is noticed and cleared. User-defined Providers are a separate product path on Providers.

## External Integrations

- CLI import checks filename collisions case-insensitively before upload and reconciles by the same name afterward. CPA's upload API has no atomic create-if-absent operation: the existing OCG mutation lock serializes OCG imports, but cannot guarantee create-only behavior against another administrative client writing the same filename concurrently.

- Explicit local CLI import is a bounded exception for source credentials: `GET /external-integrations/cpa/cli-imports` checks metadata only, while the CAS-protected `POST` reads one fixed provider path and converts allowlisted OAuth fields in memory for CPA's typed auth-file upload. Both require the local dashboard transport boundary. No browser-supplied path or token body is accepted; source files remain unchanged, OAuth payloads never enter OCG persistence or responses, and upload error bodies are suppressed. Codex, Claude Code file storage, Kimi Code, and compatible Grok OIDC entries are supported; Antigravity and keychain-only sources retain fresh login. Deterministic filenames reconcile retries without overwriting visible existing accounts. A confirmed rejection does not bump the revision; a potentially committed but unconfirmed upload consumes it and returns `unconfirmed`. Import does not change CPA auth rollback exclusions or add background synchronization.

- External integrations are static product surfaces below Settings, not Provider/Plan plugins. CPA is the current integration. OCG may use its typed V3 adapter to configure and operate a user-deployed local service, and it does not read that service's private auth files. On a Windows x64, macOS, or Linux x64 desktop or CLI Host (any build profile), OCG may also install, start, update, roll back, and stop one OCG-owned CPA child under the data directory (`cpa/versions/<version>`, `config.yaml`, `auth/`, `logs/`, `managed.json`). `managed.json` is the owner marker and stores only current/previous version, exact asset SHA-256, and loopback port — never PID or secrets. Start is manual; the child inherits only stdout/stderr, is isolated in a Windows kill-on-close Job Object or a Unix process group anchored by a transient same-executable supervisor, and dies with the app. On Unix the Host owns a close-on-exec lifetime pipe; EOF triggers bounded TERM/KILL cleanup before the supervisor releases its group identity. Log-reader shutdown is bounded even when a descendant retains an output pipe. OCG never stops, replaces, or deletes an external CPA and never kills by port or PID. Install/update are one in-memory single-flight operation against official `router-for-me/CLIProxyAPI` GitHub Releases (the matching Windows x64 zip or macOS/Linux tar.gz + `checksums.txt`), with bounded archive extraction that rejects traversal, symlinks/reparse points, and duplicate entries. Before activation, a candidate must pass health, authenticated Management/version, and the strongest non-billable Inference-Key check: authenticated `/models`; OCG does not send a billable completion during installation. One previous version/config is kept and rollback excludes `auth/`. Check/update are user-triggered. The Management password is passed only as `MANAGEMENT_PASSWORD` and is never written to `config.yaml`. The protected Inference Key and direct client keys are necessarily present in CPA's local `api-keys` config under the OCG data directory. Runtime logs are a bounded stdout/stderr tail. Removal deletes the OCG-owned `cpa/auth` directory and other canonical owned artifacts, disconnects the database, then deletes `managed.json` last; without a journal, a process crash during those earlier deletions can leave an owned but incomplete runtime, and the supported recovery is to retry removal. It never touches external CPA paths or processes. Other runtimes fail closed with an explicit unavailable reason.
- CPA accepts loopback origins on Desktop/CLI, or the fixed `http://cpa:8317` environment override in the sibling Compose profile. Redirects, embedded credentials, query/fragment URLs, remote/LAN hosts, and forwarding the client Key are forbidden. CPA inference is direct and isolated from the global outbound proxy.
- The reserved CPA account is a single route card in the ordinary account order and selector state machines. CPA's internal OAuth accounts are live projections only; logs attribute traffic to the CPA subscription pool, never a fabricated internal account. The Management Key stays encrypted in OCG storage and reaches the child only as `MANAGEMENT_PASSWORD`. The protected Inference Key is also stored encrypted in OCG, but CPA requires it — and any direct client keys — in the child's local `api-keys` config. Creating a client key still returns that secret once on the V3 response; logs and list views stay redacted. OAuth tokens remain in CPA, and node migration excludes all CPA-owned state.
- CPA catalogs may join only code-owned Aliases. Other saved IDs remain exact raw pins; conflicts fail closed. CPA receives the client Chat, Responses or Messages protocol unchanged for both known and unknown saved IDs; Gemini is converted to Chat. CPA costs and usage remain unpriced/unknown. Any CPA failure stays inside ordinary candidate fallback and must not impair existing routes.

## Aliases

- Dynamic Provider models inherit the Provider endpoint/protocol unless `upstream_override` supplies both explicitly. One effective-route resolver feeds forwarding and account model tests; auth stays Provider-owned. Override URLs use the same trusted-admin validation as Provider URLs. A keyed override whose Origin is not the persisted Provider URL (or an explicit binding `allowedOrigins` grant) refuses to send the Key; the override is not an automatic credential inheritance. Keyless definitions may still target another Origin. Public aliases sharing an exact upstream ID must resolve to the same protocol and inference URL; conflicting routes are rejected on save/import instead of selected by row order. Schema v40 stores overrides separately from template provenance. Draft tests send only the configured route, never sibling-path guesses.

- Client aliases live in `ocg_gateway::alias` (`ocg-core` `alias.rs` is the compatibility facade). Built-in Alias authority is code-owned: `ocg_domain::protocol::supported_model_ids()` supplies the original OpenCode Go namespace, while sealed exact maps supply MiniMax CN, Kimi CN, and selected GOAT long-name aliases without adding Go routes. Command first removes the Provider namespace and reuses an existing code-owned Alias; known plan suffixes such as `-paid` / `-free` are stripped only when the shorter name is already authorized. The sealed GOAT exception `nvidia/nemotron-3-ultra-550b-a55b` maps to `nemotron-3-ultra`; meaningful qualifiers such as `highspeed`, `vision-exp`, and `contributor` are not length-truncated. Saved MiniMax/Kimi catalogs activate only their sealed mappings. Unknown future Command/MiniMax/Kimi rows stay exact raw pins until code assigns them an Alias. Alias spellings are case-folded; built-in raw IDs are exact and case-sensitive, including official mixed-case MiniMax IDs and IDs containing `/`, `_`, or whitespace. Custom declared IDs retain their existing case-folded matcher. A raw ID with exactly one registry mapping is pinned to that mapping before routability is checked; an unroutable mapping is recognized but cannot produce a production route. Overlapping exact raw IDs (including an eligible Custom declared ID conflicting with another Plan mapping) return `ambiguous_model_id` without calling upstream. A Zen Free `foo-free` row always stays an exact raw pin and publishes Alias `foo` from the official `-free` suffix. Shared authorized aliases pick among Go/Zen/Command/MiniMax/Kimi/Ollama candidates in account-card persistence order. Ollama Cloud never creates or steals an Alias: a refreshed catalog may append one routeable Ollama mapping to a Go-owned alias only when stripping the `:` tag leaves exactly one catalog match (administrator matrix pins break rotation ties and are respected by later refreshes); date-tagged snapshot ids are runtime catalog data and must never be hardcoded. Eligible Custom declared IDs overlay into resolution and `/v1/models`, but must not steal already-published aliases. `/v1/models` publishes an Alias only while its exact saved catalog row exists and at least one mapping has an enabled effective protocol; all-off Provider scopes contribute no route. Forward logs distinguish `requested_model`, `resolved_alias`, and `upstream_model`; `native_cost_*` is optional. Claude Desktop's three role aliases are still rewritten before alias resolution; `/claude-desktop/v1/models` only publishes those three roles.

| Decision | Result |
| --- | --- |
| Code-owned kebab Alias | Resolves as Alias; published while a saved catalog row exists and at least one mapping has an enabled effective protocol |
| Unique raw ID | Pins to that mapping before routability is checked; unrouteable mappings are recognized but unpublished |
| Overlapping exact raw IDs | `400` `ambiguous_model_id`; no upstream |
| Zen `foo-free` | Exact raw pin always; also publishes Alias `foo` from the `-free` suffix |
| GOAT long name / suffix | Namespace stripped; `-paid`/`-free` stripped only if the short name is already authorized; `nvidia/nemotron-3-ultra-550b-a55b` → `nemotron-3-ultra` |
| MiniMax / Kimi sealed map | Saved catalog activates only code-owned mappings; unmatched rows stay exact raw pins |
| Eligible Custom declared ID | Overlays resolution and `/v1/models`; must not steal a published Alias |
| `/v1/models` publish gate | Exact saved catalog row + at least one enabled effective protocol; all-off scopes contribute no route |

## Zen Free

- Zen Free is a special built-in account without a Key; it has an account-card enable switch. When an admin clicks "Fetch Models" on the Providers page it requests the fixed official catalog, keeps only normalized valid IDs ending in `-free`, and persists the last successful snapshot. Every saved ID remains an exact raw pin, and stripping `-free` publishes that shorter name as an Alias. Refresh failures or empty results do not overwrite the old snapshot. Turn the card off when Free is not needed; when enabled it is selected along with other accounts by card order. Protocol probe controls are also on the Providers page, not the account card. Zen Free and Go use independent `cooldown_free_until`; Zen Free quotas are shared by egress IP, after a 429 the entire Free channel cools down without swapping Keys, and routing continues trying subsequent compatible cards, returning shared cooldown only when only Free candidates remain. Zen Free inference `401` is returned as-is. OpenCode Go rotates and persists `auth_error` only when the bounded JSON body has exact `/error/type == "CreditsError"`; `ModelError`, unknown, malformed, truncated, or unreadable 401 responses remain passthrough. Re-saving the same Key clears the breaker. Dashboard Ping / Key verification 401s still record `auth_error`. Free channel success rows record `cost_state=free` and do not count against Go quotas.

## Claude Desktop

- Claude Desktop uses `/claude-desktop/v1/messages` and `/claude-desktop/v1/models`; `sonnet`, `opus`, and `haiku` mappings are stored in `AppConfig.claude_desktop_models`, managed by protected `GET/PUT /dashboard/api/v3/claude-desktop/models`.

## Managed Accounts (Beta)

- `setup_step` sequence is `google_account` (UI: login identity, skippable) → `opencode_registration` → `payment` → `key_verification` → `ready`. `PATCH /dashboard/api/v3/accounts/{id}/setup` allows advancing one step or rolling back to an earlier step; skipping steps or jumping directly to `ready` is prohibited. Draft creation may edit the invite link and write it back to `opencode_invite_url` (`DEFAULT_OPENCODE_INVITE_URL` is the demo default). The dashboard edits that field on the OpenCode Go provider **Settings** tab (the legacy **Other** tab was absorbed into it). Browser targets include Google/GitHub registration and login, the invite URL, and the console at `https://opencode.ai/auth`. The managed page can open the browser via dashboard HTTP; the desktop native browser is a Host hook.

## Ollama Cloud

- The family is sealed and fixed-origin: `https://ollama.com`, Chat Completions only, Bearer, no redirects, `ProcessWideNoRedirect` proxy semantics (direction default leg; family model ids never join the per-model exception list). Protocol facts live in the family-independent seed in `ocg_domain::protocol` (`OLLAMA_CLOUD_*`); `MODEL_PROTOCOLS` must stay free of Ollama-only ids because it derives Go's published aliases. The adapter marks `WireNormalization::OllamaCloud`; the forwarder rewrites request bytes per attempt (assistant `reasoning_content` → `reasoning` when missing, `max_tokens`/`max_completion_tokens` clamped to 65535) and normalizes response/SSE frames (`reasoning`/`thinking` → `reasoning_content` backfill). Non-Ollama attempts in a mixed candidate chain must see byte-for-byte identical request bytes; `upstream_body_bytes` logs the bytes actually sent; client-facing attribution keeps the requested name.
- Pricing is manual-only from `https://ollama.com/pricing` (approved-host HTTPS redirects, content hash, CAS, last-good preservation). The official table is Model / Input / Cached input / Output; rows store quota multiplier `1.0` so `raw_cost_usd == quota_debit`, and `effective_paid_cost_usd` stays null. Runtime matching is exact first; Ollama may strip one unambiguous terminal `:` tag (`glm-5.3-flash:cloud` → `glm-5.3-flash`, dated suffixes). Cached input uses the cached price only when upstream reports cached tokens; cache creation uses the normal input price. Missing usage stays `success_no_usage`. Account billing lives in `ollama_cloud_billing` (schema v37, cascades with the account): exactly Pro `$60`, Max `$300`, Team `$1000` USD Credits per billing month. Absence of a row is unconfigured (`null` on the account field), not a Free tier. New creates require an explicit paid tier and `purchase_date`; omitting the field on update preserves state. The dashboard publishes one monthly `usd_credits` window `[purchase_date, next-month-same-day)` from `forward_logs` plus manual calibration; used credit is not clamped to the soft limit (the UI bar clamps at 100% and shows overage). Meter fullness never writes cooldown, disables accounts, or changes routing. Actual upstream 429 keeps the existing generic cooldown/fallback. Changing the stored tier clears `usage_month_window_cost_offset`; the same tier preserves it. Purchase-date changes still clear the offset. Logs are kept. Node export/import carries the billing tier. Do not call undocumented `GET /api/usage`.

## Usage Sync

- Quota for completed accounts: the official `https://opencode.ai/zen/go/v1/usage` (`go_usage.rs`) is the periodic calibration baseline; local `forward_logs` still do real-time estimation after the last successful calibration. `usage_sync.rs` coordinates manual and background paths: ready+enabled accounts with local activity in the last ~24h reconcile about hourly, inactive ones about daily; disabled/not-ready/empty-Key accounts are not auto-refreshed. Global concurrency 1, with jitter and injectable clock/jitter/fetch seams; no startup thundering herd. Manual `POST /dashboard/api/v3/accounts/{id}/usage/refresh` is still available; server-side throttling is 15s per account (success or failure counts), with concurrent deduplication, returning Retry-After / `next_allowed_at`; failures keep the last baseline and last-success. When local maximum Go usage ≥80%, accelerate reconciliation at most once every 15 minutes. Real inference 429s still write the existing cooldown/selector and additionally schedule an official reconciliation ~1–2 minutes later (not inline); official failures or `status=rate-limited` never write inference cooldown. After success, reschedule by earliest `resetsAt` (plus bounded jitter) respecting active/inactive cadence. Failure backoff: 5m → 15m → 1h → 6h. Sync metadata lives in `provider_usage_sync_state`. Shared implementation includes CAS / three-window atomic calibration and global proxy. The public Go docs have not listed this endpoint.

## Pricing, Container, And CI Notes

- Pricing is Provider-scoped: read `GET /dashboard/api/v3/providers/{provider_id}/pricing`, refresh `POST /dashboard/api/v3/providers/{provider_id}/pricing/refresh`, and write applied multipliers with `PUT /dashboard/api/v3/providers/{provider_id}/pricing/multipliers`. Go and GOAT multiplier writes are CAS-scoped to their own pricing revision; GOAT writes append a provider snapshot and affect only later request estimates. A refresh must surface multiplier differences before replacing local edits. OpenCode and Command Code use independent revisions and last-good snapshots. Each fixed official source is fetched only when the user clicks that Provider's refresh control; pricing must not auto-poll.
- After a public GitHub Release is published, `.github/workflows/container.yml` builds `linux/amd64` and `linux/arm64` images on native amd64 (`ubuntu-24.04`) and arm64 (`ubuntu-24.04-arm`) runners (smoke-tested on amd64 only), pushes each architecture by digest, then merges them into a single multi-arch OCI index under the same tag, published to `ghcr.io/klarkxy/opencode-go-mgr`. Compose uses this image by default; local source builds need `OCG_IMAGE=ocg-manager:local` then `docker compose up -d --build`.
- `.github/workflows/quality.yml` splits into three parallel jobs on PR / `main`: Web (includes `pnpm run contract:v3:check`, frontend tests/types/lint), Linux workspace Rust tests/Clippy (excluding the Tauri desktop crate; no system packages needed), and Windows Tauri-targeted tests (stubs `dist/`, does not run Vite). `release.yml` invokes the gate only for a production `v*` tag push. A `release.yml` manual candidate (even when a tag ref is selected) is always unsigned and may build only the selected platform; only a `v*` tag push event builds all three platforms and reads repository signing secrets. A production tag push triggers the release pipeline: the workflow validates that the attachment set matches assembled artifacts name-by-name (quantity derived from artifacts, not hard-coded), updater signature, public-key continuity, and GitHub server-side digest, then automatically publishes the same unchanged draft.
- Container runs fixed as UID/GID `10001` and includes `LICENSE`; Compose passes through optional `OCG_MANAGER_ENCRYPTION_KEY` to support explicit key recovery, but normal deployments still prefer keeping `.encryption-key` in the volume.

# Runtime Invariants

Behavioral invariants of the running system. Read this before changing gateway routing, aliases, Zen Free, the plan catalog, access keys, outbound proxy, usage sync, or per-Key quota recovery. Code is the source of truth; this page maps semantics that are easy to get wrong.

## Gateway And Model Lists

- Configurable HTTP catalog refresh uses `POST /dashboard/api/v4/destinations/{id}/catalog/refresh` with CAS. It derives `/models` from the saved configured route, uses only a ready credential already granted to that exact route, and rechecks destination/credential identity after I/O. Keyless routes send no secret. Discovery adds exact same-name mappings enabled with officially known or configured protocols. Existing disabled state persists only when supported by evidence or an explicit `force_off`; an unknown Auto row waits for official evidence and may be enabled when refresh adds it. Refresh preserves mappings, preferences, overrides, Key scope/grant, verification, and cooldown, while it may add documented protocol declarations. Empty/failing results do not write; truncated results retain prior rows and report truncation. Refresh never grants or expands scope. HTTP presets and Custom API share this operation; sealed catalogs retain their adapters.
- A configurable HTTP destination has either legacy route semantics (empty `protocol_routes`: its saved base URL/authentication applies to the legacy protocol set) or one to three explicit unique protocol routes. Explicit routes store the complete endpoint and authentication per protocol; the first route is the stable legacy default. Runtime materialization, grants, catalog refresh, and probing use the same route resolver. No read path rewrites a saved host or synthesizes a sibling route. A per-model upstream override remains a single authoritative route and does not add sibling protocol capability.
- GOAT protocol discovery follows its documented per-model `supported_endpoints`. Refresh adds no grant. If the operator enables a new GOAT protocol and the selected Provider Key lacks the needed route grant, the control-plane write requires an explicit selected credential authorization and saves that authorization with `force_on` in the same transaction. It does not silently add or revoke grants.

- Core Gateway: Axum + Tokio + reqwest. The same port exposes OpenAI Chat Completions / Responses, Anthropic Messages, and Gemini `generateContent` client entrypoints.
- Authenticated `GET /v1/models` lists currently-routeable Aliases from the original static OpenCode Go protocol table that have an enabled protocol in a refreshed catalog (the list is empty before the first `/models` refresh), uniquely resolved exact Go catalog IDs, plus the sealed MiniMax CN, Kimi CN, and selected GOAT long-name maps, then merges public models from saved user-defined Providers and model IDs declared by eligible HTTP credentials (enabled and ready, with a Key when authentication requires it; verification is optional). New Go IDs stay pinned to Go; discovery does not make them shared aliases. Ambiguous identities are not advertised. Saved Zen `-free` rows keep the exact raw pin and publish the suffix-stripped Alias; saved Command rows may join any code-owned Alias; saved MiniMax/Kimi rows activate only exact code-owned CN mappings. Command ids that contain `/` publish a unique last-segment lowercase kebab Alias; slash-free unmatched Command rows and unmatched MiniMax/Kimi rows remain exact raw pins. Protected `GET /dashboard/api/v4/application-models` contains Go-resolvable names with an enabled protocol from the saved catalog, independent of price coverage; an unknown price remains unpriced. Neither GET path makes upstream requests. Explicit Go directory refresh is public and keyless, independent of stored accounts, credential validity, quota, or routing cooldown. MiniMax CN / Kimi Code CN authenticated directory refresh still uses a ready stored Key even when that account is disabled for routing. Directory discovery does not verify an account. New models with documented protocols start enabled, while saved disable choices remain in effect. HTTP model IDs come from the saved destination catalog and eligible credentials' scopes. Public names turned off on **Aliases** are omitted from `GET /v1/models` and stay routable; `application-models` is not filtered. Unknown model names return `400` on all supported client formats.
- Custom model identity: an eligible Custom capability has a public model name and an exact `upstream_model`. `/v1/models` publishes only the routeable public name. Discovery yields upstream IDs and imports `public_model = upstream_model` exactly; it performs no suffix stripping or Alias synthesis. Raw conflicts are excluded from publication and resolve fail-closed as `ambiguous_model_id`. The Aliases page aggregates existing contracts and capabilities. A per-public-name switch (default on) hides that name from authenticated `GET /v1/models` without changing routing.
- Gemini clients use `/v1beta/models/{model}:generateContent` or `:streamGenerateContent` (`/v1/models/...` also accepted), may auth with `x-goog-api-key`; Gemini is only a client format, and Gateway always converts to the known model's recommended upstream protocol. Unknown model names return `400` on Chat / Responses / Messages / Gemini.
- `MODEL_PROTOCOLS` is a per-model offline protocol fallback and curated shared-alias seed, not the Go model inventory. Go/Zen/Command refresh reads official protocol documentation; only a recognized documented endpoint or documented Command family rule contributes new evidence. A failed fetch or omitted model preserves existing evidence and saved preferences. Without evidence, an unknown model has no inferred available protocol and stays Auto. Newly discovered IDs with official known or configured protocols are enabled. Existing disabled protocol/model state stays off only with support evidence or an explicit `force_off`; otherwise a later official declaration may enable the Auto row. Enabled client protocols pass through; otherwise conversion follows the saved preferred protocol and enabled adapter fallback order. No request-time protocol probing or paid discovery occurs. Operators may delete models from the persisted local catalog; that write is local-only and an official refresh may add the same ID back as an enabled new row. CPA preserves supported Chat, Responses, and Messages client protocols and converts Gemini to Chat. The request path uses the saved contract. The whole-document JSON conversion kernel is in `ocg-gateway`.
- Every OpenCode Go inference attempt carries `x-opencode-session`. An existing client value wins; otherwise the Gateway maps OpenCode's custom-Provider `x-session-id` / `x-session-affinity`, derives a stable private digest from the conversation seed, or uses the request ID only when the request has no usable conversation seed. Zen Free uses the same session header plus the official anonymous-channel identity headers (`User-Agent` containing `opencode`, `x-opencode-client`, `x-opencode-request`, `x-opencode-project`). Client-supplied OpenCode values win; otherwise the Gateway fills them after account selection (synthesized `User-Agent` is `opencode`, `x-opencode-client` is `cli`, request/project fall back to the request ID / session). Other Providers do not receive these headers. This Provider-specific identity is added only after account selection.

One logical request captures `RequestSnapshots` under the settings lock. `RoutingSnapshot` reads persisted destinations, model mappings and execution credentials directly; missing or invalid configuration fails explicitly. Compatibility Account rows and historical creation kinds do not select normal routes.

| Frozen at entry | Rechecked for every send |
| --- | --- |
| Config, transport and pricing | Credential enablement, readiness and Key version |
| Exact destination and model mapping | Destination/model/protocol still match and remain enabled |
| Original candidate identities and endpoint IDs | Current model scope, endpoint/origin grants and binding |
| Explicit alias pins | Current cooldown, shared Free gate and per-Key quota recovery |

Changed targets are rejected instead of remapped. Late authentication/cooldown results cannot update a rotated Key. Model lists, explanation and forwarding consume the same model identity and effective protocol decisions; explanation never decrypts or advances selection state.

- Shadow compare is default-off consistency instrumentation on the live materialize/resolve path, not an independent routing algorithm. When enabled it rematerializes the same planner the live request already used and compares AttemptSpec fields plus rejected outcomes; it never dual-sends and does not claim independent algorithm parity. Enable only with environment `OCG_SHADOW_COMPARE=1` (the exact trimmed value `1`). Unset, empty, `0`, and any other value leave it off. Tests may force the flag per-thread without mutating process environment.
- When protocol conversion drops optional hosted tools under the versioned `legacy_compat` profile, that marker is carried on the request plan. A runtime diagnostic is emitted at the actual forward attempt with request id, compat profile/version, and dropped hosted-tool types only — never the request body or secrets — and stored protocol configuration is not rewritten.

- Supplier cards store stable presentation membership in `settings.routing_cards_v1`. Several cards may reference the same destination. `GET /dashboard/api/v4/routing/cards` reads cards, destinations and credentials at one revision; the CAS-protected PUT commits the full card list and its flattened `credentials.routing_rank` order together. Observers never enter cards. Moving a credential between cards of its destination changes neither its authorization nor its identity, quota pool, cooldown or quota recovery. Compatibility rank-only writes reconcile the card layout without altering their requested order.

## Dashboard Control Plane: V3, V4, And V2 Tombstones

- Connection and model/protocol probes require a successful JSON response matching the requested protocol: Chat choices with message objects, Responses output without a failed/cancelled/pending status, or a Messages assistant message with content blocks. Arbitrary JSON and non-null error objects do not certify a connection. A V4 model test selects one exact saved route and an already granted ready credential; it is bounded and cannot enable a model/protocol, set preference, grant access, or write a route. Its receipt is scoped to the destination, credential version, model, protocol, and resolved configuration; changing any of those invalidates its applicability. Custom/dynamic draft probes are capped at 30 seconds per request (or the shorter configured timeout) and do not persist routing or discovered models. Responses probes use a 16-output-token budget to satisfy the observed compatible-upstream minimum. Go/Zen probes share production provider identity headers; other providers receive no OpenCode identity headers. Rotating a Custom or user-defined Key, or changing that connection's Endpoint/protocol, deletes that account's `custom_endpoint` probe observations and bumps the contract-scope revision so the old success cannot authorize the new Key or URL. Built-in catalog evidence is not wiped when a Go Key rotates.

- Dashboard V3 is a 410 tombstone at `/dashboard/api/v3`. Operational handlers live under `/dashboard/api/v4`. Control-plane changes require CAS (`expectedRevision`, `processGeneration`; price writes also need `expectedPricingRevision`). `ConnectionInfo` is the only V3 response DTO allowed to return the plaintext Open Console Gateway Key; Key-mutation responses do not include plaintext, and the client re-fetches `GET /connection`. Creating or rotating a managed CPA client Inference Key returns that CPA secret once. `GET /contract` returns the current process's live revision / generation token.
- Dashboard V4 is the sole live control plane at `/dashboard/api/v4`. It reuses V3 session middleware and its listings return the same `ControlRevision` tokens V3 uses for CAS. V4 mutations use those same CAS tokens. `POST /onboarding/commit` is idempotent by `operationId` with payload-digest binding evaluated before CAS; the same id with a different payload is rejected (`409` `operationPayloadMismatch`) and never replays. Mode `complete` requires an authorized binding when a Key already exists; it does not require the account enable switch (new ready Key cards start enabled). All objects of one commit land in one SQLite transaction; responses and stored results are secret-free. Built-in and platform-managed destinations remain immutable. Configurable HTTP destinations, including legacy Custom API connections, use CAS-protected `PATCH|DELETE /destinations/{id}`; PATCH adds safe origin grants only for explicitly selected credential ids, and DELETE refuses while any credential still references the destination. Remounted operational routes live on V4. Read-only routes include `GET /contract`, `GET /templates`, `GET /connections`, `GET /accounts`, `GET /destinations`, `GET /credentials`, and `GET /routing/explain`; those reads perform no outbound requests. Routing explain also does not decrypt secrets, write logs/cooldowns/quota recovery, or advance selector or quota-trial state. Connection ids are deterministic UUIDv5 values derived from the legacy identity, never from names or URLs. Built-ins without accounts are templates, not connections; Custom accounts are never merged by URL. Eligibility and authorization are local projections: `unknown` is not `valid`, and eligibility is never upstream health. `GET /accounts` is the identity list (`IdentityList`); `authState` is local (`unknown` is never `valid`; `valid` requires the existing verification record). `POST /credentials/{id}/rotate` is CAS-only (no `operationId`): same credential/binding ids, incremented `version` and `authStateVersion`, `authState=unknown`, and cleared account auth/verification and quota recovery so the old version cannot pollute the new Key. `POST /credentials/{id}/quota-retry` is the same CAS style with a flattened `MutationExpectation` body: it marks that credential eligible for one next normal selection, sends no outbound request, does not change enablement, and does not clear backoff; it is idempotent while already `ready` or `probing`. `GET /credentials` may include optional nullable `quotaRecovery` from local state only (absence is not verified upstream health). `PATCH /bindings/{id}` is the same CAS style and edits `modelScope` / binding `enabled` independently. `POST /identities/{id}/credentials` adds another Key that reuses the identity. New quota pools are independent by default; joining an existing pool requires explicit same-identity sharing intent. The dashboard consumes this control plane for the Providers rail, user-defined Provider creation, and the Accounts-page identity overlay (`GET /accounts`); Key rotation, binding edits and additional identity credentials use V4; remounted account, settings, auth, logs, and transfer routes also live on V4. Gateway shadow planning (`gateway::shadow`) is consistency instrumentation on the live materialize/resolve path: it rematerializes the same planner the live request already used and compares AttemptSpec fields plus rejected outcomes, without claiming independent algorithm parity or sending a second request. It is default-off; only environment `OCG_SHADOW_COMPARE=1` (exact trimmed value `1`) enables it.
- The DSH application flow is the narrow V4 route `GET|POST /applications/dsh`. GET inspects only the fixed DSH `web` profile, OCG-owned package root, compatible CLI version, and a private one-time credential handoff. POST requires the live CAS pair plus the GET fingerprint, resolves an enabled Gateway Key by id inside Core, and delegates local effects only to the registered native Host. The Desktop app and default native CLI build register the same `dsh-local-host` implementation; the official Docker image builds the CLI without that capability and returns `unsupported_runtime`. The Host invokes the official DSH plugin command with an argument array, never puts the Key in source or argv, verifies the exact package registration after the command, and on a failed install restores only the prior live handoff. The Host atomically writes or replaces only the live handoff; it never deletes `.claimed-*` files during install or rollback, because it cannot tell a stale crash remnant from the active plugin claim. Existing claims stay untouched. Live remains authoritative when both live and claims exist; that rule is what stops the Host from deleting a claim the plugin created after the Host's live write. The plugin is the sole owner of claim files: on activation it claims the live handoff by rename, imports that Key, and after a successful `credentials.set` (or after reconciling a storage failure) it deletes every `.claimed-*` sibling so `activationRequired` cannot stay stuck. Inspect reports `activationRequired` when any live file or claim exists. DSH is assumed to run one plugin `apply()` per runtime; leftover claims are crash remnants, not a second consumer. Live always wins over leftovers; if live is missing the newest leftover is pending. If credential storage fails and no newer live file exists, the claim is restored for retry. Concurrent plugin consumers are not supported: an older in-flight `credentials.set` may complete after a newer live write, but the live file remains for the next activation. Its model list comes from authenticated `GET /v1/models` at DSH list/call time; it never uses the narrower `application-models` projection.
- Provider catalog on remounted V4 is the single `ProviderCatalog` row, populated by joining destinations with sealed `BUILTIN_PROVIDERS` facts (leftover `providers` / `provider_models` tables are gone after v56). Each `ProviderCatalogEntry` carries `origin` (`builtin` | `preset` | `custom`), `editable`, `deletable`, and the row's `offering` (`plan` | `api`). Builtin rows are always `editable=false` / `deletable=false`; dynamic rows are always editable and deletable. `GET /providers/{id}` returns the union view: a builtin row yields its sealed definition; a dynamic row yields the persisted `ProviderDefinition`. `PATCH /providers/{id}` and `DELETE /providers/{id}` reject any builtin id with `400` + `code="builtinProviderImmutable"`. Builtin adapters never flow through this route. The Providers rail renders V4 destinations: built-in destinations with at least one credential, every user-defined HTTP destination (with or without a Key), and every persisted Custom API destination (with one or multiple Keys), in one searchable list. Unused built-in templates remain only in the Add Account new-service catalog and the Providers add-provider catalog, not under Existing connections. The Add Account existing-connections tab uses the same V4 connection projection as the Providers rail. `POST /providers` saves the definition; a Key on keyed auth also creates the first account in the same write, while omitting `key` leaves the definition without an account. The dashboard's create flow uses the V4 onboarding commit; remounted V4 `POST /providers` remains supported for API clients. No-auth still creates the singleton account. Deleting the last account does not delete the definition. The only "add provider" entry opens the preset browser in the main area (embedded preset form or manual form) and collects an optional Key on keyed auth. Detail is unified for every origin: models, pricing (always shown with its catalog availability state), and settings (which absorbs the OpenCode invite link). Deep links carry `connection` / `tab` / `add` / `preset`; a legacy `provider` value resolves on read to the built-in or user-defined connection with that legacy id; legacy `scope_kind` / `scope_id` values are mapped on read.
- The frontend has no closed Plan-family registry. It projects creation, filters, display names, usage and pricing directly from remounted V4 catalog rows in response order, keyed by `provider_id`; a successful empty catalog stays empty. Only a failed catalog read enables the narrow Go creation / existing Zen display fallback. First-ready model refresh reuses remounted V4 Provider Contract catalog capabilities. Provider quota windows and refresh actions follow `usageAvailability` / `manualUsageCalibration`; V4 adds only `pricingMultiplierEditable`. Proxy-list candidates are exact upstream ids from enabled Provider contracts, eligible Custom capabilities, dynamic mappings, and the active CPA catalog. Settings and the installed route set use the same builder on startup and every related snapshot change; stale persisted ids remain inert and are removed on save.
- Node migration is remounted V4 at `POST /accounts/transfer/export|preview|import` and loopback-dashboard-only; forwarded scheme headers never grant access. Export has no administrator step-up. The dashboard receives a version-1 Argon2id (64 MiB, 3 iterations, one lane) plus AES-256-GCM envelope with fixed AAD, never plaintext account or Access Keys. Password work is process-wide single-flight and runs outside settings/SQLite locks; every response is `Cache-Control: no-store`. Preview and import share decrypt/validation. Import rechecks CAS after KDF and writes the database-owned merge in one SQLite transaction. Import applies stable-ID identity semantics: package fields win on matching account/Access-Key IDs; same Plan/name with different IDs coexist; existing destination account IDs keep their current order and source-only IDs append in package order. Destination-only Access Keys and Provider scopes remain. Different-ID Key value collisions, more than 64 active sub Keys, in-bundle duplicate IDs, or any invalid row reject and roll back the whole database merge. Transfer packages carry usable ordinary accounts and verification state, ready account Keys, primary/active sub Access Keys, portable config, Zen Free state/catalog, and Provider catalogs/evidence/overrides. Matching destination rows retain local browser data plus usage/cooldown history; stale authentication and last-error flags clear with package-owned account credentials. Local quota recovery is not exported: an unchanged imported target Key retains it, and replacing the Key clears it. Source browser profiles/cookies, login passwords, referral codes, logs, usage, cooldown state, quota recovery, and unfinished managed drafts are omitted. Destination listener/root URL and OS-owned auto-start/Dock settings remain local. All fallible runtime snapshot construction reads the uncommitted merged transaction; only after it succeeds does SQLite commit, followed by an infallible snapshot installation and one revision bump.
- The cryptographic envelope remains version 1; portable content is payload V9. It carries destinations, credentials, route overrides, explicit model-resolution policy, identity/grant/cooldown extras, quota pools, observer management credentials, and node state inside the encrypted envelope. Imports accept V4–V9; V7 receives deterministic `modelResolution` defaults, while V8 and V9 require the field. Legacy Custom destinations normalize to multi-Key connection ownership without changing stable IDs or `public_only` behavior. V1–V3 and V10+ are explicit unsupported-version errors. Stable-ID merge remains transactional and preserves destination-only rows, target ordering, grants, later cooldowns, and quota pools.
- Platform parents are observer destinations (`adapter = http`, `observer_credential_id`) plus linked inference credentials. Site configuration lives on destinations + credentials after schema v54 (`platform_kind` / `platform_version` / `platform_snapshot` on the parent destination; `group_json` / link version / link snapshot on the linked inference credential). The management cipher stays on the observer credential. V4 GET stays secret-free. A linked Key stores the site root, not a complete `/v1/chat/completions` path. New API and Sub2API convert Chat Completions, Messages, and Responses themselves, so a linked Key enables those three protocols and the gateway passes a matching client format through (Gemini still converts to Chat Completions). Payload V9 carries platform destinations and observer credentials, including management secrets and platform extras inside the envelope; imported group evidence is unverified. A merge that omits the CPA observer key keeps the destination's existing management key. A package that reuses a destination platform parent ID with a different site or kind is an explicit preview/import conflict; the SQLite merge writes nothing. Each linked attempt freezes its exact model/group price, retains only native-currency estimates, and never infers wallet debit or USD cost. Refresh is manual and guards parent/link/Key identity before persisting observations. New API Key import is `POST /dashboard/api/v4/platform-accounts/{id}/import-keys`: it lists remote tokens with the stored management credential, reads each full Key, and creates associated local Custom Keys. Already stored Keys, disabled tokens, and tokens that cannot return a full Key or models are skipped; the response is secret-free. New API wallet, subscription, and Key remaining convert with the site's observed `quota_per_unit` into `usd` when that rate is known; otherwise the native `quota` unit is kept. That conversion is a display observation, not a request-cost USD inference.
- Protected V2 REST (`/dashboard/api/...`, excluding V3 and V4) returns structured `410` (`code=dashboardV2Removed`) to authorized dashboard sessions; anonymous requests get `401` first. V2/V3 auth and session, browser WebSocket, and inference entrypoints keep their existing semantics. The only preserved unversioned paths are exact `auth/status|register|login|logout` and `browser/sessions/{token}/ws`.
- `crates/ocg-core/src/dashboard.rs` handles SPA `index`/`assets` and preserved V2 auth and browser WS handlers; the tombstoned V2 REST middleware lives in `host_router.rs`. Provider model/protocol probing is the remounted V4 path `POST /providers/{provider_id}/protocol-probes`: it rejects models outside the effective Provider catalog, exposes no account selection, may walk routing-eligible accounts in saved order, and persists observations without changing protocol enablement or preference. The Accounts page uses the separate operational path `POST /accounts/{id}/model-tests` with only `{ modelId }`. It admits the model against that exact account's current scope, derives the effective protocol, and sends one minimal request through only that account. A disabled card may still be tested: the enable switch is the routing draft/live gate, not Key authorization. Binding enablement, scope, and destination grants still apply. It mutates no control-plane state, so it has no CAS; it never selects a sibling account, performs Gateway fallback, changes cooldown/quota recovery/verification/enablement, or writes Provider evidence. It is not the quota-recovery trial. The dashboard sequences **Test all** client-side and keeps results only in the open dialog. V2 account paths return `410` after authorization.
- Request observability belongs exclusively to `forward_logs`: forwarded attempts, provider protocol probes, and authenticated local parse/validation/routing failures must not be duplicated into `gateway_logs`. Pre-selection failures use unresolved/Gateway attribution with zero token fields and `cost_state=not_applicable`. `gateway_logs` is reserved for operational lifecycle/control-plane events and failures to persist or finalize a request-log row. Unauthorized requests and expected local fallbacks remain unpersisted.

## Access Keys And Auth

- On loopback listeners, every Dashboard API request (including public registration/login) requires a single `Host` naming `localhost` or a literal loopback IP. If `Origin` is present it must use HTTP/HTTPS and match that Host and port; cross-site Fetch Metadata is rejected. Native local requests may omit Origin. Forwarding headers disable local login bypass and require the existing Dashboard session. Vite preserves its original Host and Origin when proxying local development requests. Public-host reverse proxies must target a non-loopback listener, which uses single-admin login.

- The authoritative table is SQLite `access_keys` (primary Key fixed id `gateway_keys::PRIMARY_KEY_ID` / `00000000-0000-0000-0000-000000000001`, name snapshot "Primary", never disable/delete; sub-Keys are non-primary rows, active limit 64, soft-delete keeps the name but clears plaintext). Sanitized config JSON stores `gateway_key` as `""`. In-process `AppConfig.gateway_key` and `GET /dashboard/api/v4/connection` expose the live primary Key. Lifecycle is only through `/dashboard/api/v4/keys*` (including `POST /keys/primary/regenerate`). Primary/sub Key value mutual exclusion is enforced by `gateway_keys::ensure_primary_value_allowed` (v27 history in `storage-migration.md`).
- Auth collects all non-empty candidate headers Bearer / x-api-key / x-goog-api-key; any match against the credential snapshot (`CoreStateInner.credential_snapshot`, including primary Key and enabled sub-Keys) passes, with attribution to the first match in candidate-header order; the same snapshot feeds the forward log name snapshot.
- Non-loopback listeners use single-admin login. Docker can be first-initialized via `OCG_ADMIN_USERNAME` and `OCG_ADMIN_PASSWORD` (both must be set together; setting only one causes a startup error); when not provided the first registered user becomes admin.

## Persistence

- A selected preferred protocol is persisted separately from enablement. Dashboard model-override items may set preferred=true on exactly one supported protocol per model. Preference and overrides commit together; omitted/false preserves it, static reset clears it, and node transfer carries it. The effective preferred protocol uses this choice, including while disabled. Go/Zen default-Chat materialization applies only when official-docs Static evidence is absent; Zen additionally requires a `-free` model. Dynamic account DTOs omit synthetic purchase/expiry dates while preserving their stored compatibility anchors. Preference rows may belong to builtin or dynamic provider ids and `protocol` is `chat_completions | responses | messages` (schema history in `storage-migration.md`).

- A pre-identity account backfills as one identity + one credential + one All-scope binding. New ids are deterministic UUIDv5 values in the same namespace as connection ids. After schema v52 the leftover `accounts` table is gone: `credentials` hold Key material, and identity / binding / onboarding / subscription facts live on those credential rows plus `credential_grants`. A confirmed identity may hold more than one Key: `POST /dashboard/api/v4/identities/{id}/credentials` creates another credential that reuses the identity (a second product when `connectionId` differs). Platform parents and linked Keys stay separate identities: the parent holds a `platform_observer` credential (never used for inference); a linked Key's identity is `declared` with `authority_site` = parent `base_url`; the relation is declared, not verified. Do not auto-merge identities by URL, name, or key prefix, and do not claim a verified wallet. Cooldown / quota windows persist on credentials and shared-pool members. Backfill creates one quota pool per identity (`relation_confidence` unknown, `policy_mode` authoritative_limit); additional credentials are independent by default; explicit same-identity sharing joins the selected pool and raises confidence to declared. A cooldown/429 written for one member fans out to the other members. Confirmed per-Key quota exhaustion does not fan out. Shared quota is evidence from pool membership, never from matching names. Routing skips an account when its inference binding is disabled or its `model_scope` does not allow the public/routing model; default All + enabled preserves existing routes.
- Current schema is **v63**; migration history lives in `storage-migration.md`. Destinations and credentials are authoritative. `destinations.model_resolution` records `adapter_defined`, `public_only`, or `public_and_upstream`; legacy Custom rows stay `public_only`, keep their stable destination/credential IDs, and allow multiple inference credentials. Their connection configuration, including nullable explicit `protocol_routes_json`, lives once on the destination. Sealed builtin adapters stay compiled-in, platform and CPA observer boundaries stay intact, and no migration synthesizes Aliases.
- GUI data directory is Windows `%USERPROFILE%\.ocg-mgr` or macOS/Linux `~/.ocg-mgr`; CLI defaults to `~/.ocg-mgr-cli`. Upgrade, backup hashing, and failed-rollback are covered in `docs/maintainer/storage-migration.md`.
- Local account `key_cipher` / `password_cipher` uses AES-256-GCM with prefix `v2:` and body `base64(nonce || ciphertext || tag)`. The 32-byte AEAD key is SHA-256(domain || Host seed) from MachineBound / StaticKey material. Encrypt always writes v2. Decrypt accepts `v2:` only via AEAD (authentication failure is an explicit error, never a UTF-8 guess) and also reads unprefixed legacy XOR of the old 16-byte-nonce shape so directory backups restore. A successful `open_with_cipher` rewrites remaining legacy account rows to v2 in one SQLite transaction and does not log plaintext Keys. Wrong-host or corrupt ciphertext fail closed. Portable node transfer uses envelope v1; exported content is payload V11.
- Downstream access root URL priority: non-empty `OCG_CLIENT_ROOT_URL` > SQLite manual value > frontend auto-derived from production origin / dev Gateway port. Environment-variable overrides are read-only and must not be written back to SQLite.
- Desktop Gateway port priority: valid `OCG_GATEWAY_PORT` > SQLite `gateway_port` (default `9042`). The desktop Host and Vite development proxy read the same variable. The override is read-only, must not be written back to SQLite, and does not change CLI `serve --port` semantics.

## Desktop Host

- Tauri v2 cross-platform tray app; the main window is hidden by default; tray/single-instance logic opens `http://127.0.0.1:<port>/dashboard/` in the system browser, and loopback listeners skip login automatically. Host capabilities (gateway lifecycle, native browser, autostart, Dock, updater) are registered into `CoreState` and **not** registered as `#[tauri::command]` / `invoke_handler`.
- The Settings page checks the latest GitHub Release via protected `GET /dashboard/api/v4/settings/check-update`. ## Failure Facts, Recovery, And Request Budgets

- Static error profiles only decode bounded upstream evidence into `FailureFacts` (cause, scope, window, upstream reset, retry constraint, rule id/version). `failure.rs` owns the common decision. `recovery.rs` owns process-local admission, not the selector or usage ledger. Generic/unknown 429s do not invent five-minute cooldown; provider lookalike phrases outside the matching dialect or error-message field are not quota evidence.
- `Retry-After` accepts delay-seconds and supported HTTP dates. It never overwrites a quota-window reset; both constraints apply. Zero/past means no extra future wait. Valid but unrepresentably large delays stay `Unbounded`, not capped into an early retry. Endpoint constraints include exact upstream URL, model, protocol, route and an explicit proxy's identity, and are shared across Keys to that resource. Recognized per-Key quota uses its persisted credential/version/episode instead of a second process-local quota-pool probe. A Retry-After attached to that quota stays credential-scoped, independent of the quota reset, without pool fan-out or a second probe. Anonymous Free uses the existing process-wide shared-egress contract, not account-owned Key quota.
- Waiting begins around 30 seconds with small jitter and failed probes back off exponentially to 300 seconds. Only an arriving real client request performs a due single-flight probe; no background timer emits paid inference. Healthy requests remain concurrent. The map is bounded at 4096 resource slots and fails locally on capacity instead of discarding active evidence. `resource_wait` logs carry no upstream HTTP status or cost. All locally waiting candidates with no known quota reset return 503, not a fabricated reset time.
- A complete protocol-valid success can clear only its leased probe at the captured restriction revision. Invalid JSON/200, incomplete streams, unrelated errors and cancellation do not certify recovery. Late observations are checked against live authorization, explicit pool members and credential/binding generation; operator reset fences in-flight replies. The existing CAS account cooldown reset clears associated local resources but not anonymous Free. Restart clears local waits while persisted quota deadlines survive. Process-local waits do not add another schema or waiting-state UI; per-Key quota presentation and persistence are described below. Historical cooldown rows are retained.
- One logical request shares 32 attempt slots and one deadline across account fallback and same-account retries. Local skips consume a slot without sending. Non-stream uses `non_stream_timeout_secs`; stream pre-output uses `stream_idle_timeout_secs`. The deadline is applied inside send/body/pre-output phases so actual account and known HTTP status survive timeout finalization. Partial SSE frames cannot refresh the pre-output deadline indefinitely. After downstream handoff, the existing idle timeout applies, not a non-stream lifetime cap. No 408/5xx or ambiguous send/body replay is added. The existing incomplete/interrupted pre-output stream exception remains at most one same-account retry within budget; after output starts there is no replay or cross-account splicing.
- The public regressions in `gateway_resource_recovery.rs`, `gateway_request_budget.rs`, `custom_trusted_admin.rs` and `v3_runtime_invariants.rs` assert real call sequences, per-attempt logs, long-stream compatibility, reset/rotation, shared-pool isolation and deadlines. Clock sampling counts are not selection counts: recovery admission/observation also reads clocks. The two-request round-robin test proves a safe same-account retry does not advance selection.

## Usage Sync

- Quota for completed accounts: the official `https://opencode.ai/zen/go/v1/usage` (`go_usage.rs`) is the periodic calibration baseline; local `forward_logs` do real-time estimation after the last successful calibration. `usage_sync.rs` coordinates manual and background paths: ready+enabled accounts with local activity in the last ~24h reconcile about hourly, inactive ones about daily; disabled/not-ready/empty-Key accounts are not auto-refreshed. Global concurrency 1, with jitter and injectable clock/jitter/fetch seams; no startup thundering herd. When local maximum Go usage ≥80%, accelerate reconciliation at most once every 15 minutes. Real inference 429s use scope-aware recovery, or persistent per-Key recovery when recognized as quota; they additionally schedule an official reconciliation ~1–2 minutes later (not inline). Official failures or `status=rate-limited` never write inference cooldown or quota recovery. After success, reschedule by earliest `resetsAt` (plus bounded jitter) respecting active/inactive cadence. Failure backoff: 5m → 15m → 1h → 6h. Sync metadata lives in `provider_usage_sync_state`. Shared implementation includes CAS / three-window atomic calibration and global proxy. The public Go docs have not listed this endpoint.

Unrecognized temporary GOAT 429s without a usable retry constraint only exclude the account from the current request and preserve an otherwise healthy sticky target. Retry-After remains a scope-specific resource wait, not an invented quota reset. Recognized quota catalogs are under Per-Key Quota Recovery.

## Per-Key Quota Recovery

- Confirmed quota exhaustion is owned by credential id plus Key `version` and episode epoch. Routing dims that Key and skips it. Usage 100%, unknown, or failed never infers exhaustion. Official usage windows remain display-only.
- The new path does not fan out through a declared quota pool. Existing ordinary cooldown rows remain effective; new temporary errors follow the scope-aware resource rules above. Zen Free retains its separate shared-channel recovery.
- Recognized quota errors:
  - Kimi: explicit `403` naming the 5-hour, weekly, or monthly window.
  - OpenCode Go: an explicit 5-hour, weekly, or monthly window only. Structured `CreditsError` 401 may still be an inactive subscription and keeps the existing `auth_error` rotation; it is not quota recovery.
  - GOAT: strict plan-window errors persist even without a deadline; known insufficient-credits errors persist as `insufficient_balance`. Unrecognized temporary 429 follows the request-local or scope-specific Retry-After path.
  - MiniMax: `1008` and `2056`.
  - Configurable HTTP: structured `insufficient_quota` or `insufficient_balance`.
  - Unknown errors are untouched.
- Wait: a known `resetsAt` waits until that instant. `window=unknown` uses 15m → 1h → 6h (capped) and advances that step only on another proven quota error. `nextRetryAt` is the eligibility instant.
- When due, the next request the ordinary selector would send on that Key is the single trial (`status=probing`). No synthetic probe, no scheduler, and other traffic is not held awaiting validation. Manual `POST /dashboard/api/v4/credentials/{id}/quota-retry` only sets eligibility (`ready`): no outbound request, no enablement change, no backoff clear. It is idempotent while already `ready` or `probing` and may return the current row. An independent upstream Retry-After remains enforced until it expires or an explicit account cooldown reset clears that local restriction.
- Only a completed, protocol-valid successful JSON or SSE response restores the Key, including success with no usage. Timeout, cancel, or 5xx retain exhaustion, release the trial lease, and allow another try no sooner than 15 minutes without increasing the unknown-window step. A success from a stale Key version or a previous episode cannot clear the current state.
- Recovery is local and persistent. It is not exported. Import that leaves the target Key unchanged retains it; replacing the Key (including rotate) clears it.
- V4 GET listings project optional nullable `quotaRecovery` from local state only. Absence means no confirmed exhaustion, not verified upstream health. `status` is presentation (`waiting` | `ready` | `probing`).

## Pricing, Container, And CI Notes

- Pricing is Provider-scoped: read `GET /dashboard/api/v4/providers/{provider_id}/pricing`, refresh `POST /dashboard/api/v4/providers/{provider_id}/pricing/refresh`, and write applied multipliers with `PUT /dashboard/api/v4/providers/{provider_id}/pricing/multipliers`. Go and GOAT multiplier writes are CAS-scoped to their own pricing revision; GOAT writes append a provider snapshot and affect only later request estimates. A refresh must surface multiplier differences before replacing local edits. OpenCode and Command Code use independent revisions and last-good snapshots. Each fixed official source is fetched only when the user clicks that Provider's refresh control; pricing must not auto-poll.
- After a public GitHub Release is published, `.github/workflows/container.yml` builds `linux/amd64` and `linux/arm64` images on native amd64 (`ubuntu-24.04`) and arm64 (`ubuntu-24.04-arm`) runners (smoke-tested on amd64 only), pushes each architecture by digest, then merges them into a single multi-arch OCI index under the same tag, published to `ghcr.io/klarkxy/opencode-go-mgr`. Compose uses this image by default; local source builds need `OCG_IMAGE=ocg-manager:local` then `docker compose up -d --build`.
- `.github/workflows/quality.yml` splits into three parallel jobs on PR / `main`: Web (includes `pnpm run contract:v3:check`, `pnpm run contract:v4:check`, frontend tests/types/lint), Linux workspace Rust tests/Clippy (excluding the Tauri desktop crate; no system packages needed), and Windows Tauri-targeted tests (stubs `dist/`, does not run Vite). `release.yml` invokes the gate only for a production `v*` tag push. A `release.yml` manual candidate (even when a tag ref is selected) is always unsigned and may build only the selected platform; only a `v*` tag push event builds all three platforms and reads repository signing secrets. A production tag push triggers the release pipeline: the workflow validates that the attachment set matches assembled artifacts name-by-name (quantity derived from artifacts, not hard-coded), updater signature, public-key continuity, and GitHub server-side digest, then automatically publishes the same unchanged draft.
- Container runs fixed as UID/GID `10001` and includes `LICENSE`; Compose passes through optional `OCG_MANAGER_ENCRYPTION_KEY` to support explicit key recovery, but normal deployments prefer keeping `.encryption-key` in the volume.

## Billing models and observations

- StepFun CN inference remains Configurable HTTP. Ordinary API balance reads use the selected Key at `https://api.stepfun.com/v1/accounts`; `/step_plan` destinations are excluded even though they share the host. Only the returned available balance is displayed, without deriving spend or summing cash/voucher fields.
- Timed quota, cash, and credits are the three presentation models; official observation, local estimate, and unavailable describe their source independently. Go, provider-scoped prices, official API references, platform prices, and personal credits share `ocg_domain::billing` token arithmetic. Provider rate selection, multipliers, cache fallback, and observation adapters keep their specific rules. Native currencies, quota debit, and credits never become one USD total.
- A Key is one account. Supplier instances contain independent accounts and may recur in routing order, such as A1, B1, A2. Personal credit state belongs to the credential, not a supplier container or shared quota pool. Only custom_account and dynamic HTTP destinations expose configurable personal credits. New API / Sub2API linked Keys retain their existing site billing views.
- Step Plan uses local estimates and manual balance correction. Each attempt freezes exact upstream rates and the conversion factor. Completion debits current buckets in earliest-expiry order; monthly renewal and top-up expiry remain separate. Settlement and its log receipt are atomic and idempotent for JSON and streaming completion. A pending receipt is saved before sending; calibration waits for pending requests to complete. Cancellation or a cold database reopen after all prior handles close turns unfinished requests into explicit uncertainty; concurrent CLI opens leave active receipts pending. Unknown pricing or usage is not zero. Personal estimated exhaustion never changes inference eligibility, grants, cooldowns, or quota recovery.

## Official API Financial Evidence

- Matching saved `deepseek` and `zhipu` API presets can expose `model_source=official_api_preset` and financial reference pricing while inference stays Configurable HTTP. Both preset provenance and fixed destination/authentication are required; model-route overrides are checked again per attempt. Generic dynamic, Custom, Coding Plan and edited destinations do not inherit this exception.
- Additive authenticated V4 GETs `/accounts/{id}/official-api` and `/providers/{id}/official-api/pricing` are local projections. CAS-protected POSTs `/accounts/{id}/official-api/balance` and `/providers/{id}/official-api/pricing` are the only network paths. Balance requires the selected saved credential's endpoint and Origin grants, a ready Key, bounded no-redirect first-party I/O, a 15-second throttle and a post-I/O identity/CAS recheck. Public pricing fetches never carry a Key. Failure keeps prior evidence and never writes inference state.
- Reuse existing price-snapshot and credit-balance tables; no schema migration. Bind balance observations to credential ciphertext and saved destination. Delete provider-scoped reference snapshots with their dynamic Provider. GET never reparses a live web page. Prices expire after 30 days. Freeze revision/model/time per attempt; never reinterpret CNY as USD, sum currencies, debit a wallet from estimates, or reprice history. UTC-month and lifetime projections count successful locally logged requests and separately expose unknown costs for the current month.
- Source parsing validates identity, units, duplicate rows, complete DeepSeek peak/off-peak pairs and supported Zhipu non-tiered token rates. Unsupported models, stale or corrupt prices, missing usage and variable-charge requests stay unknown. Zhipu balance is explicitly unavailable, not zero. Sources and initial date are documented in the paired provider preset guide.
